# 2チャネル仮説 — 符号重み付け(logit)と OPSD(文脈)の接続

`docs/multitask_next_experiments.md` の案3を、OPSD 側と接続して一段強くした構想。
きっかけは「データセットの性質に差があるなら OPSD と絡められそう」という指摘。
測ってみたところ、**接続点は想定より遥かに鋭い**ことが分かった。

## 発端: 転移チャネルは2本あり、似ているタスク対が違う

本機構(符号重み付け)が転移を運ぶ経路は **教師のロジット**である。
そこを通れるのは「共有された出力トークン」に表現できるものだけなので、
出力形式が違えば原理的に何も通らない。実測もそうなった(Search 完全帰無、n_eff=201、p=0.85)。

OPSD/SDAR が転移を運ぶ経路は **特権文脈(自然言語のスキル)**である。
スキルは自然言語なので**出力形式に依存しない**。

そして測ってみると、**2つのチャネルでタスク間の近さの順序が入れ替わる。**

### チャネル1: 出力形式の距離(本機構が使う)

| ペア | プロンプト Jaccard | 応答タグ | 行動列挙 | 実測の転移 |
|---|---|---|---|---|
| AlfWorld ↔ WebShop | **0.80** | 同一 | 両方あり | **あり(p=1.4e-06)** |
| AlfWorld ↔ Search | 0.32 | 別 | 片方のみ | なし |
| WebShop ↔ Search | 0.30 | 別 | 片方のみ | なし |

### チャネル2: スキル(抽象)の距離

`skills/*/general_skills.md` を全件抽出して対応付けた結果:

| 抽象軸 | AlfWorld | WebShop | Search |
|---|---|---|---|
| 探索の網羅・反復 | Systematic Exploration / Avoid Redundant Rechecks | Use Result Pagination / Scan Before You Click | Decompose Then Search / Attribute-Chaining Search |
| クエリ・行動の修正 | (薄い) | **Iterative Query Refinement** | **Iterative Query Refinement** |
| 確認するまで棄却しない | Open Before Judging Empty | Confirm Hidden Attributes | Cross-Check Multiple Sources |
| 終端の規律 | Terminate Only On Success | Purchase Decisively / Conclude When Necessary | Exit When Evidence Is Solid |

**WebShop と Search は "Iterative Query Refinement" という同名スキルを共有している。**
両者ともクエリを発行して絞り込む課題だからである。
一方 AlfWorld とはスキル名の完全一致がゼロ。

つまり:

- **形式の近さ**: AlfWorld ≈ WebShop ≫ Search
- **抽象の近さ**: WebShop ≈ Search(クエリ精緻化)、AlfWorld は別系統

**WebShop は形式では AlfWorld 寄り、抽象では Search 寄りという蝶番になっている。**
これは偶然の観察ではなく、実験計画として使える解離(dissociation)である。

## 提案: チャネル解離実験

同じ3タスクに対して、2つのチャネルで別々の予測が立つ。

| | チャネル1(符号重み付け) | チャネル2(跨タスク スキル注入) |
|---|---|---|
| AlfWorld ← WebShop | **転移する**(実証済み) | 転移する(探索・終端規律を共有) |
| Search ← WebShop | **しない**(実証済み) | **転移するはず**(同名スキルを共有) |
| Search ← AlfWorld | しない(実証済み) | 弱い |

**予測の核心: チャネル1で何も受け取れなかった Search が、チャネル2では受け取る。**

これが当たれば、単独の結果より遥かに強い主張になる。

> 跨タスク転移は単一の「タスク間距離」で決まるのではない。
> **チャネルごとに異なる距離が支配する。**ロジット経路は出力形式の距離に、
> 文脈経路は抽象の距離に従う。したがって転移させたい相手に応じてチャネルを選べる。

## なぜこれが案2(Search への転移)への正しい答えなのか

前回、案2 に3つの理由で反対した。そのうち2つがこの構想では解消する。

| 前回の反対理由 | 2チャネル版での扱い |
|---|---|
| コストが高い(形式統一に教師再訓練3本) | **不要。**スキルはプロンプト文字列なので教師を触らない |
| 循環論法(似せてから転移させる) | **回避。**タスクは一切変えず、通す経路を変えるだけ |
| Search の帰無という資産を失う | **むしろ強化。**「チャネル1では帰無、チャネル2では転移」は片方だけより強い |

3つ目が特に重要である。事前登録した負の対照が**解離の片翼になる**ので、
資産を失うどころか二重の役割を果たす。

## 実装の見積もり

SDAR アーム(`claude/festive-gates-fxercy-optimizations-pqd3v2`)が既に
`algorithm.sdar.skills_dirs.{alfworld,search,webshop}` でタスク別スキルを読んでいる。
**跨タスク注入はこの配線を1本変えるだけ**で、教師も損失も触らない。

| # | 内容 | 訓練 |
|---|---|---|
| 0 | スキル本文の抽象軸マッピングを機械化(埋め込み類似度で対応付け、上表を定量化) | 不要 |
| 1 | SDAR + 跨タスクスキル注入(Search の teacher branch に WebShop のクエリ系スキルを追加) | 2本(対照 SDAR + 処理) |
| 2 | チャネル1(既存結果)とチャネル2の転移行列を並べる | — |

**ただし注意点が2つある。**

1. **SDAR は教師なしの自己蒸留であり、本機構(外部教師の符号一致)とは別アーム。**
   同じ論文に入れるなら「2チャネル」の枠組みが主で、機構は各チャネルの実装例、
   という構成にする必要がある。機構の話に SDAR を後付けすると散らかる。
2. **スキル注入は特権文脈の増量でもある。**「他タスクのスキルだから効いた」のか
   「文脈が増えたから効いた」のかを分けるには、**無関係タスクのスキルを同量注入する対照**が要る。
   チャネル1でシャッフル対照が必要だったのと同じ構造。

## 位置づけ(外部文献)

- **PromptSD (2607.18293)** は共有バックボーン+ソフトプロンプトで正の跨タスク転移を報告した
  唯一の論文であり、機構としてはチャネル2側(共有表現/文脈)に属する。
  本構想はこれと正面競合するが、**「チャネルによって支配する距離が違う」という主張は
  PromptSD にはない。**そこが差別化点になる。
- **SDAR (2605.15155)** はスキル条件付き特権文脈を自己蒸留に使うが、
  **タスク内**に閉じている。跨タスク注入は素直な拡張であり、上流論文の自然な発展として書ける。

## 判断

案3(距離の分析)の骨格はそのままに、**距離を1次元ではなく2チャネルに拡張する**のがこの構想である。
Sokoban(形式は近く意味は遠い)と Search(形式は遠く抽象は WebShop に近い)の2点が揃うと、
「形式の距離」と「抽象の距離」を直交する2軸として分離できる。

推奨: `docs/multitask_next_experiments.md` の step 0(訓練不要の転移可能性行列)を
**両チャネルぶん測る**ところから始める。チャネル2側の距離は
スキル文の埋め込み類似度で訓練なしに測れるので、コストはほぼ変わらない。
