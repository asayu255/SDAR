# 検証を再現可能にする — `ROLLOUT_ASYNC_GENERATE=0` 一つだけ

**結論だけ読む人へ。** 比較に使う検証（val-only）は `ROLLOUT_ASYNC_GENERATE=0` で走らせること。
他の高速化は全部そのままでよい。これだけで同一チェックポイントの再検証が**バイト単位で一致**し、
所要時間はむしろ短い（5m00s 対 5m18s）。アーム間・チェックポイント間の差は 100% 重みに帰属できる。

```bash
ROLLOUT_ASYNC_GENERATE=0 VAL_ONLY=1 VAL_CKPT=<...>/global_step_N \
    bash examples/opd_grpo_trainer/run_..._qwen3.sh
```

---

## なぜ必要か

alfworld 単独 run の検証得点は、同じ run の中で 25 step ごとに 9〜12 pt 振れていた。その一部が
測定誤差なのか方策の実体なのかを決めるため、`global_step_250` を 10 回再検証したところ
**SD 1.60 pt**（95% CI 1.10–2.92）だった。この 1.60 pt は全部が下記の機構由来である。

## 原因は 1 つの「組」

2026-09-14、`global_step_250`、各 2〜3 回、**90 ゲーム分の生成テキストの SHA** で突き合わせた。

| 機構 | 2 回の一致 | 全部オフとの一致 | 判定 |
|---|---:|---:|---|
| 全部オフ（基準） | 90/90 | — | 決定的 |
| `ROLLOUT_ASYNC_GENERATE` のみ | 90/90 | **90/90** | 無影響 |
| `ROLLOUT_KEEP_VLLM_AWAKE` のみ | 90/90 | **90/90** | 無影響 |
| `ENV_RESET_PREFETCH` のみ | 90/90 | **90/90** | 無影響 |
| 行スキップ 3 種<sup>†</sup> | 90/90 | **90/90** | 無影響 |
| `enable_prefix_caching` | 90/90 | 8/90 | 決定的だが**値が変わる** |
| CUDA グラフ（`enforce_eager=False`） | 90/90 | 10/90 | 決定的だが**得点が 0.756→0.778** |
| **async + keep-awake** | **62/90** | 6/90 | **非決定** |
| **上記 + `ENV_RESET_PREFETCH`** | **45/90** | 6/90 | **非決定**（2 回再現） |

<sup>†</sup> `ROLLOUT_SKIP_DONE_PREPROC` / `ROLLOUT_DECODE_ACTIVE_ONLY` / `ROLLOUT_COMPACT_RECORD`

**片方だけなら無害で、両方揃ったときだけ壊れる。** `ROLLOUT_ASYNC_GENERATE` は「ランクごとに
1 つのエンジンを連続的に回す」経路を開き、`ROLLOUT_KEEP_VLLM_AWAKE` はそのエンジンをターンを
跨いで生かす。両方あって初めて、**どのリクエストが同じ decode ステップに乗るかが到着タイミングで
決まる**ようになり、logits が動き、vLLM の共有 RNG の引き順も変わる（リクエスト単位のシードは
pump 経路にしか入っていない。`generation_output.seed_for_prompt` 参照）。

非決定モードでの同一チェックポイントの得点は 0.744 / 0.756 / 0.789 / 0.800 / 0.800 / 0.811 と
**6.7 pt** に散った。起動時の GPU はいずれも 15 MiB（空）で、近隣プロセスによる KV キャッシュ量の
変動ではない。

## なぜ async を切る側を選ぶか

どちらを切っても組は壊れるが、

1. `KEEP_VLLM_AWAKE=0` は vLLM が**毎ターン sleep/wake する**モードで高い。
2. **検証では async は速度に寄与しない。** keep-awake ありで実測 7.10 / 7.25 分（async あり）
   対 6.98 / 6.92 分（async なし）。126 リクエストが同時に走るのでエンジンは既に飽和しており、
   非同期投入が埋める駆動側の空き時間がない。学習では事情が異なる（そちらでは効く）。

## 併せて注意：推論設定そのものが得点を動かす

prefix caching を入れると 90 ゲーム中 **82 ゲームで生成テキストが変わり**、CUDA グラフでは
**得点が 2.2 pt 動く**。どちらも内部的には再現するので噪音ではなく、設定ごとに別の点に着地する
だけである。したがって **異なる推論設定で採点したアーム同士は比較できない**。intent lock は現在
「性能ノブは対象外」としているが、**検証に使う推論設定はロックに入れるべき**である。

## 学習側はどうするか

**やらないこと。** 学習の非決定性はロールアウト経路だけではない（FSDP/NCCL の縮約順序、backward の
非決定的カーネル、search のリモートリトリーバ、Ray のスケジューリング。`torch.use_deterministic_algorithms`
はこのツリーでは `verl/workers/megatron_workers.py` でコメントアウトされたまま）。残った非決定性は
300 step で増幅するので、部分的な決定化は何も買わない。そして本質的に、学習で測りたい量は
「この手法が生む結果の分布」であり、ビット再現する 1 本はそこから 1 点を誤差棒なしで返すだけになる。
必要なのは**複数シード**である。

学習で決定性が役に立つのは 1 箇所だけ：**コード変更が control 経路を変えていないことの検査**。
パッチ前後で 3〜5 step 走らせてビット比較すれば、intent lock より強い保証になる。

## 対応するダンプ側の変更

同じ作業で、検証インスタンスのダンプに **`extra.gamefile`** を追加した
（`_record_turn` が行に載せ、`_validate` → `_dump_val_instances` が書く）。
`_dump_val_instances` の docstring が対応キーと呼んでいる `val_index` は、**マルチターンでは
対応キーにならない**（1 軌跡が最大 50 行を持ち、長さがチェックポイントごとに違うので、行 i は
毎回別のゲームを指す）。`gamefile` はゲーム単位で一意なので、これで対応のある比較ができる。

副産物：検証の 126 軌跡が引いている**別々のゲームは 90 個**しかない（60 ゲームが 1 回、24 が 2 回、
6 が 3 回）。実効サンプル数は 126 ではない。

## 再現手順

`/tmp/.../scratchpad/` の `det_rep.sh`（全部オフ）、`abl_rep.sh` / `abl3_rep.sh`（1 系統ずつ）、
`rec_rep.sh`（採用設定）。ダンプは `~/val_instances/alfworld_only_noise/` に残っている。
