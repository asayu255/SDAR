# 次の実験の選択 — 3案の評価と推奨

前提: `docs/multitask_sign_weighting_results_150.md` の結論
(前半 AlfWorld 加速 p=1.4e-06、Search 完全帰無、後半は AlfWorld ゼロ・WebShop 有意に劣化)。

## 決定的な材料: Sokoban が既に実装されている

6環境のプロンプト類似度(Jaccard)と出力形式を実測した:

| | AlfWorld | WebShop | **Sokoban** | Search | AppWorld | GymCards |
|---|---|---|---|---|---|---|
| AlfWorld との Jaccard | — | **0.80** | **0.44** | 0.32 | 0.13 | 0.15 |
| 応答タグ | think/action | think/action | **think/action** | think + search/answer | think/code | image |
| 行動空間の列挙 | あり | あり | **あり** | なし | なし | なし |
| 意味領域 | 家事 | 買い物 | **格子パズル** | QA | API操作 | カード |
| 最大ターン | 50 | 15 | 15 | 4 | — | — |

**Sokoban は「形式は AlfWorld/WebShop と同じ、意味は完全に無関係」という唯一の点である。**
`env.sokoban.mode` で `tiny_rgb_array`(テキスト盤面)を選べるので、
Qwen3-1.7B(非VL)で既存3タスクと同じレシピで訓練できる。
`examples/gigpo_trainer/run_sokoban.sh` が既にある(視覚モード指定なので mode の変更が要る)。

これにより、前回立てた反証可能な予測 —
**「転移を決めるのは意味ではなく出力形式である」** — が直接検定できる。

## 3案の評価

### 案3(タスク間距離の分析)= 推奨・骨格

**最も価値が高い。**現状の主張「AlfWorld と WebShop は似ているから転移した」は
ほぼ同語反復だが、**「転移の有無は実験前に測れる量で予測できる」**なら運用可能な一般主張になる。

Sokoban を足すと予測が判別的になる:

- Sokoban が転移する → **形式が条件、意味は不要**。強く一般的な主張
- 転移しない → Jaccard 0.80 は転移、0.44 は不転移、0.30 も不転移という**用量反応の3点**が得られ、
  閾値の所在が分かる

**どちらに転んでも報告価値がある。**良い実験の条件を満たしている。

### 案1(近いタスクの転移をさらに強調)= 単独では逆効果。アニーリングと必ず組で

実測が示すのは、機構の書き換えが**後半には錘として働く**こと
(WebShop 後半 p=1.6e-07 で有意に劣化)。強調を上げれば錘も強くなる。

一方で余地はある: 目標移動量は `teacher_kl` の 2〜4%、OPD 項は損失全体の 3〜6%。
**係数を上げる余地は数値上ある。**ただし前半だけ効かせ後半で切らないと、
今回観測した劣化を増幅するだけになる。

したがって案1は「係数を上げる」ではなく **「係数を上げる + アニーリング」** が正しい形。
ATOD (2606.27814) の annealed OPD→RL が同じ問題への外部処方箋であり、本機構と直交する。
**5アーム超えを 300step で狙える唯一の路線**でもある。

### 案2(Search への転移)= 今はやるべきでない

3つの理由で反対する。

1. **Search の帰無は現在の最大の資産である。**事前登録された負の対照であり、
   n_eff=201(自己相関ほぼゼロ)で p=0.85。転移させたらこの対照を失う。
2. **コストが高く比較可能性を壊す。**引継ぎ資料 §11 の「案F インターフェース統一」の
   再掲になる: Search を `<action>` 形式に変えるとデータセットのプロンプト変更になり、
   **Search 教師が旧形式で RL 訓練済み**なので教師再訓練+ベースライン再測定で計3本。
   Search-R1 系との比較可能性も失う。
3. **循環論法になる。**「転移させるためにタスクを似せる」は結論の先取りである。

ただし**測定としては残す価値がある**: Search が本当に「形式が違うから転移しない」のか、
単に**飽和して測れない**だけなのかは未分離。引継ぎ資料 §8 が挙げた
`{data_source}_success_rate` 内訳、`<answer>` 無し打ち切り率、`prompt_length/clip_ratio_search`
(`truncation: left` で質問文が落ちる事故)は訓練不要で測れる。**案3の一部として実施する。**

## 推奨する順序

| # | 内容 | 訓練 | 得られるもの |
|---|---|---|---|
| 0 | **既存3教師で転移可能性行列を測る**(‖δ_m‖ の 3×3、タスク対ごとの符号一致率、教師の交差ロールアウト成功率)。Search の飽和診断も同時に | 不要 | 予測子を既存データで検証。κ が実測の転移(AlfWorld◯/Search×)を再現するか |
| 1 | **Sokoban テキストモードの単一タスク教師** | 1本 | 判別点の追加 |
| 2 | 4教師で行列を再測 | 不要 | **予測子の確定/反証。案3の核心** |
| 3 | 予測が当たれば **{AlfWorld, Sokoban, Search} 3タスク + 重み付け** | 2本(対照+処理) | 意味的に無関係なタスク間の転移の実証 |
| 4 | 並行して **案1: 係数増 + アニーリング**(既存3タスク) | 2本 | 300step で5アーム超えを狙う性能アーム |

step 0 が最優先である理由: **訓練コストゼロで、案3の予測子が既存データで機能するかが分かる。**
機能しなければ Sokoban を訓練する前に設計を見直せる。
v2 提案 §8 に書いて一度も実行していない測定であり、ここで回収する。

## 主張の変化

現状: 「本機構は AlfWorld を加速する(ただし後半で消え、WebShop では害になる)」
→ 弱い。単一タスクの単一シードの利得。

案3 完遂後: **「跨タスク転移の有無は、出力形式の距離という事前に測れる量で予測できる。
本機構はその予測どおりに働き、予測が『効かない』と言う場所では効かない」**
→ タスク対の選択に依存しない一般主張になり、新しいタスク対への適用可否を
実験前に判断できる。

会議通過確率の観点でも、こちらの方が「性能で勝つ」路線より現実的である
(N=126・1.7B の制約下で性能勝負が成立しにくいことは既に確認済み)。
